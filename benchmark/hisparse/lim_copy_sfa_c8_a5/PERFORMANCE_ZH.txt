A5 C8：128K/64K/16K -> 1K，C2048/C4096 的整网性能对比
====================================================

固定测试矩阵（1K=1024 tokens）
----------------------------
输入 131072 / 65536 / 16384，输出固定 1024，C 分别为 2048 / 4096。
TopK K 始终是 2048；C 是每请求稳定前缀的持久 HBM cache 容量，额外 tail 区不计入 C。
每个 C 都分别运行普通 C8 baseline 与 C8 + LIM + Copy-SFA，共 4 次服务启动，
汇总为 6 行 A/B 对比。默认客户端并发为 1，排除长上下文下容量不足导致的排队。
baseline 仍使用 C8 KV 和相同模型、并行拓扑、预算、DeepEP、overlap、graph；
只关闭 sparse offload/LIM/Copy-SFA。两边都关闭 MLAPO 与 radix cache。
结果是组合方案的整网收益，不能拆成某个算子的加速比，也不是 C8 相比 BF16 的收益。

只需拉取 SGLang 的 feat/hisparse-lim-copysfa-c8-a5 分支，Kernel 保持已经验证的
988ad6d wheel，不需重编。需要通过更新后的 container.sh serve 重新启动本次服务，
新启动会保存 launch.json，绑定模式、PID/进程启动时间、两仓提交、包版本和选定环境。
客户端只访问容器内本机 HTTP，自动查找同一个 C8_RESULTS_DIR 下的存活 manifest；
缺失、PID 已退出、模式错误或服务/客户端提交不同都会停止测试。

0. 生成四份长上下文配置
----------------------
128K 输入 + 1K 输出至少要求 context_length=132096；原来的 36864 不够。
原来的 max_total_tokens=131072 也放不下一个完整请求。脚本从你已验证的 C8_CONFIG
复制配置，在副本末尾固定覆盖 context=132096、max_total_tokens=147456、C/模式和
测试矩阵。原配置文件保持不变，其他模型/拓扑/通信等设置沿用原配置。

  export C8_CONFIG=/workspace/c8-a5.env  # 改为你现有配置的实际路径
  export C8_SCRIPT=/mnt/share/wzy/sgl-sglang/benchmark/hisparse/lim_copy_sfa_c8_a5/container.sh
  bash "$C8_SCRIPT" perf-configs

记下生成目录，例如：
  export PERF_CONFIGS=/workspace/c8-a5-results/perf-configs-20261024-120000-123

目录中有：c2048-lim_copy_sfa.env、c2048-baseline.env、
c4096-lim_copy_sfa.env、c4096-baseline.env。两个终端都设置相同的 C8_SCRIPT 与
PERF_CONFIGS。这里每份配置都已固定模式，不再依赖 LIM_EVAL_MODE 的环境覆盖。

147456 是为这次单并发长上下文实验设置的总 token 预算，不代表一定适配每套 A5
模型显存。服务必须实际启动成功。baseline 若装不下相同预算，不能仅降低 baseline
预算后继续声称同配置加速；需使用两边都能运行且至少覆盖 132096 tokens 的相同值。
同时修改四份配置后重跑。A5 C8 的物理源池含 padding 必须 <=262144，沿用现有校验。

1. C2048：先优化，再 baseline
----------------------------
只停止自己当前前台启动的本次测试服务，等待其 NPU 进程退出；不停止其他服务。
终端一启动优化服务，等待 ready：
  C8_CONFIG="$PERF_CONFIGS/c2048-lim_copy_sfa.env" bash "$C8_SCRIPT" serve

终端二：
  C8_CONFIG="$PERF_CONFIGS/c2048-lim_copy_sfa.env" bash "$C8_SCRIPT" perf lim_copy_sfa

记下输出的 perf-* 目录，命名为 OPT2048。终端一 Ctrl-C 停止该服务并等待退出，再：
  C8_CONFIG="$PERF_CONFIGS/c2048-baseline.env" bash "$C8_SCRIPT" serve

ready 后终端二：
  C8_CONFIG="$PERF_CONFIGS/c2048-baseline.env" bash "$C8_SCRIPT" perf baseline

记下结果目录为 BASE2048。

2. C4096：同样两次启动
---------------------
终端一先停止前一个测试服务并等待退出，再启动：
  C8_CONFIG="$PERF_CONFIGS/c4096-lim_copy_sfa.env" bash "$C8_SCRIPT" serve

ready 后终端二：
  C8_CONFIG="$PERF_CONFIGS/c4096-lim_copy_sfa.env" bash "$C8_SCRIPT" perf lim_copy_sfa

记下结果目录为 OPT4096。终端一停止该服务并等待退出，再：
  C8_CONFIG="$PERF_CONFIGS/c4096-baseline.env" bash "$C8_SCRIPT" serve

ready 后终端二：
  C8_CONFIG="$PERF_CONFIGS/c4096-baseline.env" bash "$C8_SCRIPT" perf baseline

记下结果目录为 BASE4096。baseline 本身不使用 C cache，仍各测一次作为同时间段
对照，估计测量漂移；不能把 baseline 的重复测量差异解释成 C 的收益。

3. 一次汇总六行结果
------------------
终端二把以下变量替换为各次实际输出的目录，按顺序传入：
  BASE2048=/workspace/c8-a5-results/perf-实际目录1
  OPT2048=/workspace/c8-a5-results/perf-实际目录2
  BASE4096=/workspace/c8-a5-results/perf-实际目录3
  OPT4096=/workspace/c8-a5-results/perf-实际目录4
  bash "$C8_SCRIPT" perf-compare "$BASE2048" "$OPT2048" "$BASE4096" "$OPT4096"

也可先只对比一个 C：
  bash "$C8_SCRIPT" perf-compare "$BASE2048" "$OPT2048"

输出 comparison.md / comparison.csv / comparison.json，列出 C、输入/输出长度、
并发、baseline/优化吞吐、加速比、平均及 P95 TTFT/TPOT、端到端平均延迟。
脚本拒绝不完整/有失败的结果，以及协议、模型/精度、拓扑、预算、graph、overlap、
PrefillDelayer、DeepEP、两仓提交、包版本、选定通信环境不同的结果。每对 A/B 的 C
必须相同；两对之间只允许 C 不同。保留 serve-* 的 server.log 和 launch.json。

测量协议与有效性
----------------
每组先发 1 个预热请求（仓库客户端预热输出 32 tokens，不计入指标），随后发 4 个
正式请求，固定生成 1024 tokens、ignore_eos=true、temperature=0。完整三档矩阵
重复 3 轮，每个工作负载共 12 个正式请求。每次启动 9 个 case、36 个正式请求、
36864 个正式生成 token；四次共 144 个正式请求、147456 个生成 token，另有预热。

复用 python -m sglang.benchmark.serving --backend sglang，流式返回，要求
stream_interval=1，MTP/其他 speculative decoding 关闭。本地生成自然语言合成清单，
无需下载数据；仓库 random loader 用 seed=42 重复/截断输入，--tokenize-prompt
保持精确 token 数，--random-range-ratio 1 固定输入/输出长度。各轮原始 JSONL、
命令、日志、逐请求长度和延迟保留，数据 SHA256 必须相同。
合成文本的重复内容会影响 TopK/cache 命中分布；结论限于此工作负载，正式报告建议
再用你的真实长文本复测。性能检查不判断答案正确率，精度仍使用 GSM8K 等独立评测。

每轮要求全部请求成功、错误为空、输入长度准确、输出恰好 1024 tokens、首 token
计时有效、服务配置不变。失败/超时将非零退出并保留 status=fail，部分成功不能拿来
计算收益。每次结果包含 npu-smi 前后快照；测试时独占这组卡，不并行运行 GSM8K、
smoke 或其他压测。客户端不启动/关闭服务、不自动重试、不修改 DeepEP/graph/overlap。

output_throughput = 完成的输出 token 总数 / 正式请求批次持续时间，包含 prefill、
调度与 decode，是整网输出吞吐，不是纯 decode 算子吞吐。
TTFT = 请求发出到第一个非空流式 token 的时间，包含服务端排队和 prefill。
TPOT = 每个请求 (端到端延迟 - TTFT) / (输出 tokens - 1)，用于观察 decode 阶段。
每个工作负载跨 3 轮取中位数，不把不同输入长度/C/并发混成一个总加速比。
吞吐加速比 = 优化吞吐 / baseline 吞吐，大于 1 为加速。
延迟降低 = (1 - 优化延迟 / baseline 延迟) × 100%，正数为降低，负数为回退。
CSV/JSON 保留吞吐 min/max；P95 为每轮 P95 的跨轮中位数，每轮 4 个样本的 P95
仅供参考。小于测量波动的变化需要增加请求数/轮数复测。正式结论建议交换测试顺序
再跑一对，排除温度、频率、其他负载和时间漂移的影响。

可调整轮数/请求数（所有模式/C 必须一致）
------------------------------------
生成的配置固定了默认协议，可用显式参数覆盖，例如：
  C8_CONFIG="$PERF_CONFIGS/c2048-lim_copy_sfa.env" \
    bash "$C8_SCRIPT" perf lim_copy_sfa --rounds 5 --waves 8

也可先只跑 16K 快速确认，再使用默认完整矩阵：
  C8_CONFIG="$PERF_CONFIGS/c2048-lim_copy_sfa.env" \
    bash "$C8_SCRIPT" perf lim_copy_sfa --input-lengths 16384 --rounds 1

增大并发前，确认 max_total_tokens 和物理源池容量。128K 单请求已占大部分 147456
预算，并发 8 不等于实际 decode batch=8；脚本会对超预算并发打印 NOTE。默认并发 1
就是为先获得这六组明确可比较的长上下文结果。每个 case 默认 3600 秒超时，
--case-timeout 可覆盖；超时只结束该 case 客户端，服务留在前台供检查。

脚本自身验证（2026-10-24）
-------------------------
Bash 语法、Python lint/format、15 类离线 shell 参数/退出状态检查通过。
真实仓库 serving 客户端已对 CPU HTTP/SSE fixture 跑通多轮、不同输入/并发的两种
标签及最终 4 请求协议；配置不一致、请求错误、长度不符、无首 token 时间会拒绝。
另验证了四份配置覆盖原配置固定值、两个 C 汇总、中位数及加速/回退符号计算。
这些是客户端与控制流程验证，没有运行 A5 模型，也没有产生 A5 性能收益结论。
