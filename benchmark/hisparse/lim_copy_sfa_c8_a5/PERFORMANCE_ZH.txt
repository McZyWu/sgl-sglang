A5 C8 整网容量与吞吐：以平均 TPOT 约 50 ms/token 为目标
===================================================

10-26 更新：本流程代替原来的固定并发 1 实验。
普通 C8 baseline 关闭 sparse offload/LIM/Copy-SFA；lim_copy_sfa 打开这三项。
模型、权重精度、拓扑、mem_fraction_static、overlap、PrefillDelayer、DeepEP 一致。
每种模式独立扫描客户端并发，寻找可接受 TPOT 下最高的整网输出吞吐。
C=2048/4096，K=2048；输入 131072/65536/16384，输出严格为 1024 tokens。
目标平均 TPOT 50 ms/token；按用户允许“50 多也可以”，默认候选上限为 <60。
每轮都须低于候选上限；报告同时保存平均/P95 TPOT、是否低于 50、TTFT 和吞吐。
--tpot-limit-ms 可调整上限。这里的最优只代表已扫描点；边界最优需扩展扫描。

为什么旧实验失败/不适合找最大吞吐
---------------------------------
1. 旧 context=132096 恰好等于输入+输出。worker max_req_len=context-1，
   scheduler 再保留 1，因此实机四个请求都被裁成 1022，errors 为空。
   新配置 context=135168，新客户端先检查输入+输出+2 与实际 token 容量。
   仍要求满 1024；不会把短输出当成通过。
2. 旧 max_total_tokens=147456 对 128K 最多容纳约一个完整请求，增加客户端
   并发通常只增加排队。新配置默认清空该显式上限，由各模式按同一 0.8 等
   mem_fraction_static 和实际内存预算确定 token 池。保留实际 max_total_num_tokens。
3. 旧 --cuda-graph-bs-decode 16 只捕获 [16]。新配置使用 [1,2,4,8,16]，
   避免所有小 batch 补齐到 16；最大请求数先保留 16，不盲目扩大预分配 DRAM。
4. Copy-SFA 的 2048 blocks 限制是每请求的 block-table 宽度，即最多 262144
   tokens 的行（含 req_to_token 额外列和 padding）。不是全局 indexer token 池
   上限。新生成器允许总池 >262144，同时限制 context<=262140。

生成配置，只生成一次并固定目录
----------------------------
终端一（C8_CONFIG 使用你原来验证过的配置路径）：
  export C8_CONFIG=/workspace/c8-a5.env
  bash "$C8_SCRIPT" perf-configs

记下上一步实际打印的目录，例如（替换为实际值，两个终端必须相同）：
  export PERF_CONFIGS=/workspace/c8-a5-results/perf-configs-实际日期时间PID

会生成四个 env：c2048-baseline、c2048-lim_copy_sfa、c4096-baseline、
c4096-lim_copy_sfa。原配置保持不变。基线不使用 C，第二组 baseline 是重复对照。
默认初筛并发 2/4/8/16，1 轮，每轮请求数=并发*2；每档预热并发个请求、输出最多32，
预热不计入指标。正式输出始终1024、ignore_eos=true、temperature=0。
128K prefill很耗时，初筛后在最佳点附近用 --rounds 3 --waves 4 复测；
正式比较两边使用一致轮数/波数。默认每个case超时14400秒，可用--case-timeout改。

comparison.md/csv：每个 C、每档长度，分别列 baseline 和优化的最佳客户端并发、
吞吐、TPOT、倍率；无候选点显示 N/A。all-points.csv 保留全部并发曲线和P95等。
comparison.json 记录每种模式实际池容量、启动配置与 NPU HBM 快照。
每次 perf 的 slo-summary.json 也单独给出该模式的所有点和最佳点。
性能数据跨轮中位数，门槛要求每轮都满足，不混合不同长度或 C。
输入为固定seed的合成inventory文本，仓库random loader重复/截断到精确token长度；
重复内容会影响TopK/miss分布，结论限于该工作负载，可再用真实长文本复测。

允许为找峰值调整 max_total_tokens、max_running_requests、graph buckets，
比较器将这些差异明列；其他受检查配置/源码/环境和工作负载必须一致。
不能把独立最优点倍率称为“相同 batch 的算子加速比”。

进一步扩大 batch
----------------
先看每个 perf 的 server_info.json 中 max_total_num_tokens、internal_states 里的
memory_usage/effective_max_running_requests_per_dp，再看实际 Decode batch 日志。
客户端并发不等于活跃 batch；脚本从 serve-*/server.log 截取各 case 的日志样本，
记录 decode batch 的 min/median/max（含预热，按scheduler/DP，不是graph补齐大小）。
未启用日志或无样本将标为未知，不从客户端并发推断 batch。

若最优落在16、TPOT尚可，并且主机DRAM和HBM足够，可另生成32档配置：
  C8_CONFIG=/workspace/c8-a5.env bash "$C8_SCRIPT" perf-configs \
    --max-running-requests 32 --concurrencies 2 4 8 16 24 32
用新目录重新启动、重新扫描。此步骤会扩大主机DRAM预分配与graph/通信需求；
现有每rank DeepEP dispatch cap=32，只在实际含padding的token数<=32时适用。
更大batch需要先核对并一致调整两边通信容量/窗口，不能直接把并发改成64/128。

DRAM每rank约 R * align128(context+4) * 656 * 本地KV层数，R含预留行。
TP8下各rank独立分配；增加 max_running_requests 会线性增加DRAM，并不因 C 较小
而免除完整 host KV。16K/64K 专项如需更大batch，可降低 context 减少DRAM；
对应 baseline/优化需相同context，并用 --input-lengths 16384 等单独测、单独汇总。

指标及内存解释
-------------
TPOT=request(端到端延迟-TTFT)/(输出token-1)，再对请求求平均；P95也保留。
吞吐=总输出token/正式批次墙钟时间，含prefill、排队、decode、batch爬升/收尾。
batch增大通常先摊薄权重/算力开销、增加吞吐；随后计算、indexer、DRAM访问、
通信和prefill干扰可能拉高TPOT，甚至吞吐回落。因此按实测曲线选点，不外推。
128K prefill 很长；即使decode更快，整网吞吐也可能仍受prefill影响，TTFT必须同看。

npu-smi 的 HBM usage 是 used/total。例如79321/98304 MB已用约77.5GiB，
剩约18.5GiB/卡。8卡余量不能直接合并成一张卡空间。
同一mem_fraction_static自动池实验会把节省的HBM转成更大indexer池，因此总HBM
可能接近；收益表现为更多token容量/活跃请求和吞吐，不能仅凭空闲HBM判定节省。
需要“同等token容量下少占多少HBM”，另生成 --max-total-tokens 147456 的匹配
容量配置，只比较HBM；该128K容量仍难支持大batch，与找最大吞吐的实验分开。
保存的npu-smi是设备整体的测试前/后快照，不是进程净分配或连续采样峰值。

所有请求须成功且长度精确。失败即非零退出，performance.json保留active_case、
原始JSONL/log路径和错误；不能使用失败/部分结果计算收益。
测试时独占本次卡组，勿并行GSM8K/smoke。客户端不自动启动/停止服务。
可选offload诊断见 OFFLOAD_TRACE_ZH.txt；性能测试必须关闭，客户端会检查。
